This directory, tests, contains tests which exercise parts
of the ABINIT package.

These tests are designed primarily to exercise parts of the code
quickly, NOT necessarily to give physically sensible results.
For greater speed, some tests are not run to full convergence.
Also the quality parameters (especially ecut) are minimal, i.e.
the calculations are underconverged.

Most of them are ran through the runtests.py utility. Type

    $ runtests.py --help

to get help.

There is a small README file in the subdirectories that contain the input and reference files.
The documentation related specifically to one test is appended to the input file of this test,
and can also be accessed through `runtests.py`  (aka `runtests.py -l`).

Also, typing

    $ make help

will give information on the use of the make command in the present directory.
`make` mostly relies on `runtests.py`,
but also triggers some other actions, in which runtests.py is not used.

## Adding a new test

New tests should normally be added to an existing test suite.
Choose the suite that best matches the feature being tested and inspect nearby tests before creating a new one.
Using a similar test as a starting point helps keep input parameters, tolerances, and metadata consistent.

A test suite generally has the following layout:

```text
tests/SUITE/
├── __init__.py
├── Input/
│   └── tNN.abi
└── Refs/
    └── tNN.abo
```

To add a test:

1. Add the ABINIT input file to `tests/SUITE/Input/`.
2. Append a `TEST_INFO` section to the input file as described below.
3. Add the expected output files to `tests/SUITE/Refs/`.
4. Register the input filename in the suite's `tests/SUITE/__init__.py` file.
5. Run the test locally and review all numerical differences.

Keep tests small and focused.
They should exercise the intended code path without using production-quality convergence parameters.
A test should preferably run in less than 10 seconds, and tests longer than 30 seconds should have a strong justification.

Do not replace or weaken an existing test merely to add coverage for a new feature.
If a reference output changes, verify that the change is physically and numerically justified before updating the reference file.

## Registering a test

Each suite contains an `__init__.py` file with an `inp_files` list.
Add the new input filename to this list:

```python
inp_files = [
    "t01.abi",
    "t02.abi",
    "t03.abi",
]
```

The input file must be present in the suite's `Input/` directory.
Prefixing a filename with `-` disables the test without deleting its registration:

```python
inp_files = [
    "t01.abi",
    "-t02.abi",  # Disabled.
]
```

Suite-wide requirements can also be declared in `__init__.py`.
For example, `need_cpp_vars` specifies the preprocessor definitions required to enable the suite, and `keywords` adds common selection keywords to all its tests.

Some suites define named subsuites in the `subsuites` mapping.
Use this mechanism when a related group of tests should be selectable independently with `runtests.py`.
Suite and subsuite names must be unique across the entire test suite.

Creating an entirely new suite requires additional registration:

1. Create `tests/NEWSUITE/__init__.py`, `Input/`, and `Refs/`.
2. Define `inp_files` and any suite-wide requirements in its `__init__.py`.
3. Add `NEWSUITE` to `_tsuite_dir_names` in `tests/__init__.py`.
4. Run a dry-run selection to confirm that the suite and its tests are discovered.

The test database is regenerated by default when `runtests.py` is invoked.
The `--use-cache` option deliberately reuses `tests/test_suite.cpkl` and should not be used after changing `TEST_INFO` or an `__init__.py` file unless the cache has already been refreshed.

## Writing the `TEST_INFO` section

Every input file ends with a commented `TEST_INFO` block.
It tells the Python test runner which executable to launch, which auxiliary files are needed, which result files to compare, which tolerances to apply, and how the test should be classified.

The block uses INI syntax between special markers, and every line begins with `#%%` so that ABINIT treats it as a comment:

```ini
#%%<BEGIN TEST_INFO>
#%% [setup]
#%% executable = abinit
#%% [files]
#%% files_to_test = t03.abo, tolnlines=0, tolabs=0.0, tolrel=0.0
#%% psp_files = PseudosGTH_pwteter/13al.pspgth
#%% [paral_info]
#%% max_nprocs = 1
#%% [extra_info]
#%% authors = A. Developer
#%% keywords = NC
#%% description =
#%%   Short description of the feature and code path exercised by this test.
#%%<END TEST_INFO>
```

Start new comparisons with strict tolerances:

```ini
tolnlines = 0, tolabs = 0.0, tolrel = 0.0
```

Relax a tolerance only after examining the differences on the supported compilers and architectures.
The tolerance fields have different meanings:

- `tolnlines` is the maximum permitted number of differing lines according to the selected `fldiff` mode.
- `tolabs` is the maximum permitted absolute numerical difference on an individual line.
- `tolrel` is the maximum permitted relative numerical difference on an individual line.

Use existing tests for the same executable as examples because executables may require additional fields.
Parallel tests can define processor-specific sections such as `[NCPU_4]` and declare suitable values for `nprocs_to_test` and `max_nprocs`.
Chained tests declare the ordered `test_chain` in the first input of the chain (the head) and usually use `pre_commands` or `post_commands` to transfer files between steps.
The other members of the chain do not need to repeat `test_chain`; if they do, the list must be identical to the one given in the head.

The complete automatically generated list of supported `TEST_INFO` sections and options is available with:

```sh
python3 -m tests.pymods.testsuite
```

Run this command from the top-level ABINIT directory.

Further documentation is available in:

- [`doc/developers/testsuite_howto.md`](../doc/developers/testsuite_howto.md), for suite organization, registration, tolerances, parallel tests, and chained tests.
- [`doc/developers/new_testsuite.md`](../doc/developers/new_testsuite.md), for YAML-based output validation and the `[yaml_test]` section.

YAML validation is activated for an output by adding `use_yaml = yes` or `use_yaml = only` to its `files_to_test` entry.
The optional `[yaml_test]` section then specifies either an external YAML file, relative to the input file, or a short inline YAML test definition.

## Running and checking a new test

Run commands from the top-level ABINIT directory unless stated otherwise.
First check that the runner discovers the test without executing it:

```sh
./tests/runtests.py 'SUITE[NN]' --dry-run
```

Then execute it:

```sh
./tests/runtests.py 'SUITE[NN]'
```

For a parallel test, specify the maximum number of MPI processes, for example:

```sh
./tests/runtests.py 'SUITE[NN]' -n 4
```

Independent tests can be executed concurrently with `-j NUM` (`--jobs`), which starts `NUM` Python worker processes.
The members of a chain are always executed sequentially inside the same worker.
Use `-j 0` to let `runtests.py` choose the number of workers from the available CPUs.
OpenMP threads are set with `-o NUM` (`--omp_num-threads`), which exports `OMP_NUM_THREADS` for each run.
This option cannot be combined with `-c`: in this case, specify the OpenMP variables in the configuration file.
The three options can be combined, for example:

```sh
./tests/runtests.py v9 -j 4             # 4 workers, sequential runs
./tests/runtests.py paral -n 2 -j 2     # 2 workers, each test with 2 MPI processes
./tests/runtests.py v9 -o 2 -j 4        # 4 workers, each run with 2 OpenMP threads
```

The total number of CPUs used is roughly `(MPI processes) × (OpenMP threads) × (workers)`.
Keep this below the number of physical cores to avoid oversubscription; `runtests.py` prints a warning when the machine is overloaded.

The results are written under `tests/Test_suite/` by default.
Inspect the standard output, standard error, test report, and numerical differences rather than relying only on the final pass/fail status.

Useful discovery commands include:

```sh
./tests/runtests.py --help
./tests/runtests.py --show-info
./tests/runtests.py 'SUITE[NN]' --list-tests-info
```

Before committing a new test, check that:

- The test is registered and selected by its expected suite identifier.
- The `TEST_INFO` metadata parses without errors.
- All pseudopotentials and auxiliary inputs are declared.
- Every file named by `files_to_test` has an intentional reference file.
- Tolerances are justified and no broader than necessary.
- The description explains what capability or regression is covered.
- Keywords and authors are valid and useful for test selection.
- The test passes in the intended sequential or parallel configurations.
